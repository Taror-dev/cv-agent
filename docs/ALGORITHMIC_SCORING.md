# Алгоритмическая оценка: экспериментальный движок и спецификация

Состояние на 06.10.2026: реализованы словарный baseline, выделение фактов,
локальный клиент эмбеддингов, кэш SQLite, экспериментальная формула, CLI и
отображение объяснений в карточке и маркировка метода в таблице вакансий.
`algorithmic.v3` учитывает явные предпочтения города/формата работы; SQLite v15.
В v3 исправлено распознавание офисных задач: слово office само по себе больше
не исключает фрагмент опыта из смыслового сравнения.
По умолчанию остаётся LLM-оценка:
калибровка и проверка качества на вручную размеченных вакансиях ещё предстоят.

## Экспериментальный режим с векторами

Клиент использует native Ollama `/api/embed`, отдельно от генеративной модели.
Текущий кандидат для пилота — `qwen3-embedding:0.6b`; он сравнен с BGE-M3
на синтетических сценариях. Выбор ещё не подтверждён реальной ручной разметкой.
При первичной установке потребуется скачать веса.
Данные вакансий и документов направляются только в настроенный local/LAN
Ollama endpoint; перехода на облачный или генеративный провайдер нет.

Модель установлена 06.10.2026 и прошла настоящую синтетическую проверку:
3 из 3 запросов DE/RU/EN выбрали ожидаемый фрагмент, размерность — 1024.
Время одного холодного прогона — 16.111 с (включает загрузку модели и служебные
запросы). Digest и значения сходства сохранены в
`docs/benchmarks/qwen3_embedding_smoke.json`. Это проверка подключения и
нескольких простых сопоставлений, не доказательство качества оценки вакансий.
Временный сервер завершён; для рабочего score нужен работающий embedding server.
Лицензия исходной модели — Apache 2.0:
[официальная карточка Qwen](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B).

```bash
# После запуска локальной Ollama: отдельная установка весов.
ollama pull qwen3-embedding:0.6b

# Проверка на синтетических фрагментах DE/RU/EN, без CV и production DB.
PYTHONPATH=src .venv/bin/python -m cv_agent.embedding_smoke

# Предварительный отчёт текущего профиля, без замены сохранённых баллов.
PYTHONPATH=src .venv/bin/python -m cv_agent.cli score \
  --engine algorithmic --preview --report /tmp/cv-agent-algorithmic-preview.json

# Явно заменить оценки текущего профиля результатами экспериментального движка.
PYTHONPATH=src .venv/bin/python -m cv_agent.cli score --engine algorithmic --verbose
```

Отчёт создаётся как новый файл с правами 0600 и содержит фрагменты документов.
Preview сохраняет кэш векторов и extraction metadata, может обновить описание
вакансии через источник, но не меняет её оценку. Повторное использование того
же имени отчёта запрещено, чтобы не затереть прежний результат.

`scripts/check-local-embeddings.sh` устанавливает модель, использует уже
работающий loopback-сервер или временно запускает свой и завершает его после
синтетической проверки. Вес модели сохраняется в обычном каталоге Ollama;
отчёт и серверный лог — в отдельном `/tmp/cv-agent-embedding-smoke.*`.

В `criteria.yaml` появился раздел `scoring`: engine, веса, ограничения и
`embeddings` (model, dimensions, batch_size, timeout, base_url, expected_digest,
query_prefix, document_prefix, num_ctx). Пустой base_url берётся из OLLAMA_HOST;
URL ограничен loopback/явным приватным IP, без редиректов и учётных данных.
Настройки LLM_MODEL/провайдера писем на модель эмбеддингов не влияют.

Схема SQLite v15 хранит векторы по account_id, сущности, роли, текстовому хэшу
и идентификатору backend. Backend включает реальный digest модели, размерность,
префиксы, context и версию подготовки текста. Digest проверяется до и после
вычислений; его смена в процессе вызывает ошибку, а не смешение версий.
`expected_digest` позволяет дополнительно закрепить требуемую ревизию.
Неизменившиеся фрагменты переиспользуются; повреждённый кэш пересчитывается.
Смена backend заменяет старые векторы данной сущности после успешной обработки.
Удаление документа/профиля/вакансии очищает связанные векторы. Миграция создаёт
консистентный backup существующей схемы и проверена на временных базах v12/v13.
Миграция v14 добавляет account-scoped `candidate_profiles.scoring_preferences`;
существующие контакты, документы, баллы, векторы и application status сохраняются.

Native `/api/embed` получает `truncate: false`; превышение окна возвращается
как ошибка. Один общий flock-слот ограничивает одновременно вычисляемые
эмбеддинги. Задания отдельно учитывают embedding requests и время очереди.
Генеративный клиент в алгоритмическом score не создаётся; ошибка модели
сохраняется как score_error, не как score=0. В этом режиме неподходящие и
неоценимые вакансии не удаляются физически.

Предварительная формула использует веса 40% навыки, 30% задачи, 20% языки/
образование/стаж и 10% регион. Задачи объявления сопоставляются с фрагментами
опыта CV, без curriculum. Сходство линейно переводится во вклад между
similarity_low=0.45 и similarity_high=0.85; это стартовые непроверенные пороги.
Сходство задач не подтверждает конкретный навык, стаж, язык или диплом.
Явное несоответствие обязательному условию ограничивает балл настраиваемым cap
(49 по умолчанию), без дополнительного штрафа за тот же факт. Unknown не
вызывает cap и не означает, что кандидат навыком не владеет.

Нераспознанные компоненты пока получают вклад 0 и показываются как unknown;
веса не перераспределяются. Без явных предпочтений города/формата работы
компонент location остаётся unknown; при стандартных весах максимум тогда 90.
При подтверждённой совместимости или явно выбранном отсутствии ограничений
location может добавить до 10 баллов. Смысловые сопоставления задач остаются
кандидатами для ручной проверки и сами по себе не дают подтверждённое покрытие.
Это существенное ограничение пилота, а не завершённая шкала пригодности.
`--missing` в новом режиме включает устаревшие оценки; входы, полное описание,
версия правил, веса и backend влияют на актуальность. `--force` пересчитывает
балл, но позволяет переиспользовать подходящие векторы.

Для возврата к LLM использовать `score --engine llm --force`; результаты
успешных расчётов остаются в artifacts, application status не меняется.
Веб-поиск использует engine из criteria.yaml. Генерация ключевых слов, если
она нужна, и подготовка писем продолжают использовать генеративную модель.
Карточка показывает компоненты, их вклад в балл, исходные фрагменты и причину
ограничения суммы из-за обязательного требования. В таблице есть отдельный
столбец «Способ оценки» с фильтром ИИ/Алгоритм и метка «Предварительная».
Числовые фильтры и сортировка сохраняются. Ошибка любого движка обозначается
«ошибка оценки», без утверждения, что модель обязательно вернула неверный формат.
В карточке доступна история последних 20 успешных записей artifacts выбранной
вакансии текущего аккаунта: дата UTC, балл, метод, модель и версия.
Ошибки/unscored не выдаются за успешные числовые результаты. История до внедрения
artifacts не восстанавливается из выдуманных данных. Входы разных расчётов могли
отличаться; эти баллы не являются автоматически сопоставимой шкалой.

## Города и формат работы

В профиле кандидата появились отдельные поля для алгоритмической оценки:

- Формат: «Не задан», «Любой формат», «Полностью удалённо», «Гибридный»,
  «Только на месте». «Любой формат» — явное отсутствие ограничения; значение
  «Не задан» сохраняет unknown, не добавляет баллов.
- До 20 допустимых городов, через запятую. Пустой список при выбранном формате
  означает отсутствие ограничения по городам. При невыбранном формате и пустом
  списке весь location остаётся unknown. Названия дедуплицируются.

Внутри location половина веса относится к формату, половина — к городам.
Нормализация городов ограничена регистром, пробелами, Unicode NFC и начальным
почтовым индексом. Сравниваются целые названия из поля места вакансии; ни
подстроки, ни перевод Munich → München, ни расстояние между городами не выводятся.
Несколько мест разделяются запятой, точкой с запятой, `|` или `/`. Если ни одного
точного совпадения нет, статус unknown: исходное поле может содержать регион,
филиал или адрес, а не однозначный город. Это не доказанное несоответствие.
При заданном списке городов он проверяется и для удалённых вакансий: алгоритм
не выводит, что удалённая вакансия автоматически доступна из любого города.

Формат подтверждается только явными маркерами в описании: например, `fully remote`,
`100% remote`, `vollständig im Homeoffice`, `полностью удалённая работа`,
`hybrid`, `ausschließlich vor Ort`, `on-site only`. Bare `remote` и
`Homeoffice möglich` не доказывают полную удалённость. Отрицания, указания
возможности и противоречивые маркеры остаются unknown/conflict. Явно другой
формат даёт mismatch в мягком компоненте location, без cap для обязательных
квалификаций. Цитаты и шаблонные объяснения сохраняются в отчёте.

Эти предпочтения не изменяют параметры поиска. Адрес, город для футера резюме,
поисковый регион и radius не превращаются в предпочтения автоматически.
Не проверяются расстояние, время дороги, право на работу, ограничения налогового
резидентства и применимость удалённой работы из конкретной страны.
Изменение предпочтений меняет candidate_hash; `--missing` пересчитывает балл,
но неизменившиеся векторы текста остаются в кэше. Версия алгоритма изменилась
на v2, поэтому оценки v1 требуют пересчёта при следующем score.

Официальные источники для адаптера:
[Ollama embed API](https://docs.ollama.com/api/embed),
[Qwen3 Embedding](https://github.com/QwenLM/Qwen3-Embedding),
[Ollama qwen3-embedding](https://ollama.com/library/qwen3-embedding).

## Что уже можно запустить

Из корня проекта:

```bash
PYTHONPATH=src .venv/bin/python -m cv_agent.scoring_benchmark \
  --dataset docs/benchmarks/scoring_seed.yaml \
  --split holdout --output /tmp/cv-agent-score-holdout.json
```

По умолчанию оценивается отложенная часть. `--split calibration` запускает
часть для настройки, `--split all` — диагностический прогон всего набора.
Отчёт содержит баллы, извлечённые требования, подтверждающие фрагменты,
статусы, время работы, Precision@k, Recall@k и NDCG@k. `--k` задаёт размер
верхней части ранжирования, по умолчанию 10.

Для сравнения с уже полученными LLM-оценками можно передать `--llm-scores`
с JSON вида `{"python/sql_support": 80, "java/integration": 92}`. Сравнение
выполняется только на одинаковых парах. Внешняя модель при этом не вызывается;
провайдер, модель и условия получения старых баллов должны быть описаны
рядом с исходным файлом. LLM-оценки не являются эталонной разметкой.

Бенчмарк не читает production DB, реальные CV и API-ключи. Он не изменяет
вакансии и не вызывает сеть или генеративный LLM. Отчёт с полными фрагментами
пишется только в явно указанный файл; такой отчёт с настоящими документами
нельзя считать обезличенным.

## Исходные данные и происхождение

`scoring_rules.Document` содержит стабильный ID, тип документа и текст.
Каждый `Fact` и `Requirement` содержит `Evidence`: ID документа, тип, начало
и конец фрагмента в извлечённом тексте и сам фрагмент. Позиции относятся к
извлечённому тексту, а не к байтам PDF; номера страниц не выдумываются.

`scoring_inputs.collect_scoring_inputs(store)` собирает данные только
выбранного аккаунта. По умолчанию отдельный бюджет равен 60 000 символов
на файл и 200 000 на документы. Он не зависит от LLM-провайдера. Сохраняются
границы строк; превышение бюджета и ошибки извлечения входят в предупреждения.
Структурированные языки профиля тоже являются источником фактов. Контакты
профиля не включаются в текст для правил. Глобальный `profile.yaml` этот
экспериментальный сборщик не читает; политика legacy fallback будет определена
при интеграции рабочего score, без заимствования данных у другого профиля.

Хэш входов включает account_id, содержимое/тип/хэш файлов, языки, регион и
явные предпочтения профиля, ограничения обработки. Он используется для
инвалидации оценки; кэш векторов отдельно зависит от текстов и backend.
Метаданные документов обновляются через
существующий account-scoped Store; оценка вакансий этим сборщиком не записывается.

## Правила первого прототипа

| Ситуация | Решение |
|---|---|
| JavaScript в CV, Java в вакансии | Java не подтверждена |
| Postgres / PostgreSQL, NodeJS / Node.js | Явные словарные эквиваленты |
| Python только в учебной программе | Учебное упоминание, без подтверждения рабочего опыта |
| Немецкий B2 в документах, требуется C1 | Явное несоответствие уровня |
| Написано «хороший немецкий» без CEFR | Уровень не подтверждён |
| B2–C1 | Консервативная нижняя граница B2 |
| «Планируемый/целевой C1» | Текущая квалификация не подтверждена |
| Разные языковые уровни в источниках | Конфликт; ручная проверка |
| Нет сведений о требуемом навыке | Не подтверждено; без автоматического отказа |
| «Нет навыков Python» | Явное отрицательное утверждение |
| «Python не требуется» в объявлении | Не создавать требование |
| Технология в блоке «Мы предлагаем» | Не создавать требование к кандидату |
| Требование повторяется | Учитывать один раз, с наибольшей явно заданной важностью |
| Bachelor или Master | Одно требование с альтернативами |
| Обучение на Bachelor ещё идёт | Завершённая степень не подтверждена |
| Общий стаж и отдельное упоминание Python | Не доказывают столько же лет работы с Python |
| Явно «5 лет опыта с Python» | Сравнить с явно заданным требованием по Python |
| Диапазон стажа 3–5 лет | Использовать нижнюю границу 3 |
| Календарные даты работы | Пока не вычислять стаж по датам |

Важность требования: mandatory / desirable / unspecified. Явные маркеры
распознаются на немецком, английском и русском. Если обязательность и
желательность смешаны в одной неделимой фразе, важность считается неоднозначной.

Статусы сопоставления:

- `confirmed`: исходные сведения подтверждают требование;
- `mismatch`: есть явные сведения о несоответствии;
- `unknown`: подтверждения недостаточно;
- `conflict`: источники противоречат друг другу.

Автоматического отбрасывания вакансий по этим статусам в прототипе нет.
Объяснения создаются немецкими шаблонами, без выдуманных фактов.

## Формула baseline

Это простая контрольная точка для сравнения, а не веса экспериментального движка
40/30/20/10 из дорожной карты. Вес обязательного требования — 3,
неуточнённого — 2, желательного — 1. Вклад подтверждения — 1, учебного
упоминания навыка — 0.25, неподтверждённого/конфликтного/отрицательного — 0.

`score = 100 × сумма(вес × вклад) / сумма(весов)`

`coverage` — доля веса требований с определённым результатом (`confirmed`
или `mismatch`). При недостаточном покрытии `preliminary = true`. Unknown
остаётся в знаменателе: отсутствие информации не повышает балл. Unknown
не становится утверждением об отсутствии навыка и не вызывает отказ.
Баллы разных движков нельзя считать эквивалентными без калибровки.

Если документов, извлекаемых фактов или требований нет, `score = null` и
сохраняется причина (`candidate_unavailable`, `candidate_facts_unavailable`,
`requirements_unavailable`). Это не нулевая пригодность.

## Набор проверки и ограничения выводов

`docs/benchmarks/scoring_seed.yaml` содержит шесть синтетических профилей и
десять синтетических объявлений: 60 пар кандидат/вакансия. Это **не 60 разных
вакансий**. Ожидания сценариев заданы отдельно от алгоритма: 2 — подходит,
1 — пограничная, 0 — не подходит. Их ещё не подтверждал пользователь.

Шесть групп вакансий относятся к calibration, четыре — к holdout. Разные
версии одной группы не могут попасть в обе части; загрузчик это проверяет.
Сводный отчёт seed сохранён в `docs/benchmarks/seed_baseline_report.json`.

Precision считает только grade=2. NDCG дополнительно учитывает grade=1.
Метрики считаются и по каждому профилю, и по общей диагностической выдаче.
При десяти вакансиях на профиль Precision@10 охватывает почти весь набор;
его нельзя интерпретировать как проверку качества реального top-10 поиска.
Общая выдача разных профилей тоже не является рабочим пользовательским сценарием.

Для завершения этапа 1 ещё нужны 50–100 разных обезличенных вакансий,
ручная разметка пригодности, baseline текущего LLM на том же наборе и
согласованный критерий качества. Проверка synthetic seed этого не заменяет.
Текущие замеры времени включают только правила в памяти, без загрузки PDF,
внешних моделей и векторизации; это не оценка скорости будущего pipeline.

Текущий парсер ограничен словарём и явными формулировками. Свободный текст,
составные отрицания, неоднозначные группы требований и отраслевые степени
нужно расширять по независимым контрольным примерам. Калибровка сходства задач,
география с координатами и подтверждённый стаж по датам относятся к следующим этапам.

## Дальнейшая проверка

### Сравнение моделей и подбор порогов

`scoring_evaluation.py` сравнивает словарный baseline с настоящими локальными
эмбеддингами через ту же формулу, что используется в score. Входы задаются
явными файлами; модуль не открывает production DB, папки CV или клиент LLM.
Синтетический набор `scoring_tasks_seed.yaml` содержит 5 профилей и 12 вакансий:
60 пар, из них 40 calibration и 20 holdout. Есть задачи DE/EN/RU и случаи,
где учебная программа или близкий по смыслу текст не подтверждают точное условие.

```bash
# Ollama должна работать; обе модели предварительно установлены.
PYTHONPATH=src .venv/bin/python -m cv_agent.scoring_evaluation \
  --dataset docs/benchmarks/scoring_tasks_seed.yaml \
  --models docs/benchmarks/local_embedding_models.yaml \
  --k 3 --output /tmp/new-local-model-comparison.json

# Отдельная явная установка и сравнение на синтетике.
bash scripts/compare-local-embeddings.sh
```

Отчёт сохраняет digest моделей, настройки, полные сравнения, число запросов,
время первого/повторного прогона, Precision@k/NDCG и precision/recall/F1 при
заданном min_score. Случаи unscored остаются отдельными, не становятся score=0.
Подбор cosine-интервала и min_score использует только calibration. Holdout
оценивается после выбора; предложение не меняет criteria.yaml. Веса пока не
подбираются. Для воспроизведения чисел используются неокруглённые сходства;
округление вклада совпадает с рабочей формулой.

Настоящий прогон 06.10.2026: Qwen — 11.38 с, BGE-M3 — 23.72 с; повторный
прогон — около 0.09 с у обеих моделей, без embedding-запросов. На этом простом
holdout все методы дали одинаковую классификацию. Подробности и ограничения:
[сводка](benchmarks/local_model_comparison_2026-10-06.md) и
[полный JSON](benchmarks/local_model_comparison_2026-10-06.json).
Это GPU-прогон с первоначально пустым кэшем векторов в памяти. Он не измеряет
CPU, пиковую RAM, скорость извлечения PDF или производственный кэш SQLite.

Для импорта ранее полученных LLM-оценок используется `--llm-scores FILE`.
Файл JSON должен содержать version=1, dataset_hash итогового размеченного
набора, provider, model, prompt_version и scores вида
`{"candidate-1/vacancy-001": 75}` (допустим null). Загрузчик отвергает другой
набор, неизвестные ID и некорректные числа. Все методы сравниваются на одном
подмножестве пар; облачный провайдер автоматически не вызывается.

### Постепенные отзывы в карточках

Для обычной проверки не требуется редактировать YAML или оценивать весь пакет.
В карточке под описанием и переводом появился блок «Ваша оценка вакансии» с
кнопками «Подходит» (2), «Сомнительно» (1), «Не подходит» (0). Пояснение
необязательно, до 2000 символов. Нажатие выбранной кнопки сохраняет ответ вместе
с текущим пояснением. Существующий ответ можно изменить, сохранить только
пояснение или убрать. Автоматический балл и статус отклика не меняются.

SQLite v15 добавляет vacancy_reviews с ключом (account_id, refnr) и каскадным
удалением при удалении вакансии/аккаунта. Сохраняются оценка, пояснение, UTC-дата,
хэши источников и закрытый снимок текстов документов/вакансии для последующей
проверки. Снимок использует отдельные лимиты алгоритма и выбранные типы
документов. Сохранение не обращается к источникам, embedding server или LLM;
извлечение документов может обновить extraction metadata, но не исходные файлы.
Миграция создаёт штатный backup существующей DB; повторный запуск идемпотентен.

Если исходные документы, язык, предпочтения, тип документа, title/company,
место или описание изменились, старый отзыв помечается требующим проверки.
Изменение автоматического балла, перевода или даты поиска не инвалидирует
отзыв. Подписанный контекст формы привязан к сессии, аккаунту, вакансии и
версиям входов; устаревшая форма отвергается с сохранением черновика пояснения.

Уже накопленные ответы выгружаются без ручного изменения файлов:

```bash
# Новый каталог с существующим родителем; достаточно нескольких отзывов.
PYTHONPATH=src .venv/bin/python -m cv_agent.scoring_review \
  --from-feedback --output-dir data/benchmarks/new-card-feedback
```

Экспорт читает только текущий аккаунт через SQLite mode=ro, использует именно
снимки на момент ручной оценки и сохраняет готовые grades/reasons. Разные
версии документов представлены отдельными профилями candidate-NNN. Похожие
title/company и точные дубликаты текста не расходятся между calibration/holdout;
остальные близкие версии ещё нужно проверить. Каталог 0700, файлы 0600.
Без отзывов с текстом или двух независимых групп экспорт сообщает об отсутствии
достаточных примеров. В calibration для подбора порогов нужны подходящие и
другие примеры. Использование автоматического балла при оценке возможно:
это практическая обратная связь, а не независимая слепая проверка качества.

### Закрытая выборка для отдельной ручной проверки

`scoring_review.py` экспортирует сохранённые описания только текущего аккаунта.
Соединение SQLite открывается mode=ro/query_only без Store и миграций. Старые
баллы не читаются, объявления не обновляются, сеть и модели не вызываются.
Документы сохраняют вручную выбранные типы, структуру и отдельные лимиты score.
Символические ссылки не читаются. До storage migration нужен каталог cv/<user>;
экспорт не использует общий legacy CV-каталог в качестве fallback.

```bash
# Родитель каталога должен существовать; указанный каталог обязан быть новым.
PYTHONPATH=src .venv/bin/python -m cv_agent.scoring_review \
  --count 100 --output-dir data/benchmarks/new-private-review
```

Созданный 06.10.2026 пакет находится в `data/benchmarks/review-2026-10-06/`:
dataset.yaml, sources.json и инструкция README.md. В нём 100 различных
описаний, по 25 из четырёх источников, 80 calibration / 20 holdout и документы
одного текущего профиля. Каталог имеет права 0700, файлы — 0600, data/ исключён
из git. Тексты могут содержать персональные данные: пакет ещё не обезличен.

Выбор — чередование источников и сортировка по хэшу описания, без старых оценок.
Точные дубликаты исключаются; одинаковые title/company принадлежат одной части.
Близкие дубликаты с разными заголовками нужно проверить вручную. Выборка по
источникам не является случайной оценкой всего потока поиска.

В judgments заполните 0/1/2, в review_notes — основания, обязательные условия
и подтверждающие сведения. После независимой проверки всего набора замените
label_source=pending_human_review на human_reviewed_v1. Незавершённую разметку
benchmark не принимает. Затем используйте ту же команду scoring_evaluation
с новым путём dataset.yaml, k=10 и новым выходным JSON. Для общей проверки
сервиса ещё нужны другие профили, отдельное обезличивание и сохранённые
LLM-оценки на точно этих входах.

Следующие шаги — сравнить локальные многоязычные модели на достаточном наборе,
доработать извлечение требований и регион, откалибровать веса/пороги, провести
пилот с ручной проверкой. Только после проверки качества новый механизм заменит
LLM-оценку по умолчанию. Офлайн-тесты на фиксированных векторах проверяют
механику, но не являются доказательством качества настоящих эмбеддингов.
