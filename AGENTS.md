# AGENTS.md

## What this repo is

A job-application agent for Ilia Rerich (Wangen im Allgäu): searches vacancies (Arbeitsagentur API, StepStone, LinkedIn, get-in-it), scores them against his CV, generates German Anschreiben, and prepares application dossiers (semi-automatic — the user submits manually).

Documents are account-scoped under `cv/<profile>/`; the default profile contains
the German CV and Russian AI curriculum. Supported active upload/extraction
formats are PDF (text layer), UTF-8 TXT, and MD.

Document-driven pipeline: `cv_agent/documents.py` has an extension registry for
PDF (pypdf text layer), UTF-8 TXT and MD. Blank image-only PDFs are retained but
reported as requiring OCR; unsupported office formats are rejected before
upload. Account-scoped extraction metadata lives in SQLite `documents` (schema
v10). A manually selected `cv` type overrides filename inference; CV is ordered
before curriculum/certificates/other and a strict purpose-specific character
budget is applied (`keywords`, `scoring`, `letter`). Budgets come from
`criteria.yaml` `document_limits` keyed by LLM backend class — `external`
(cloud providers, larger budgets) vs `ollama` (local model, conservative
defaults); the class is derived from the primary provider config without a
liveness probe, and prompt templates no longer re-truncate collected documents
(prompt versions scoring.v2/keywords.v2/letter.v3). The profile UI previews
extracted/included character counts and errors. Account-scoped `artifacts` keep
provider/model/prompt version, timestamp and input hashes; vacancies distinguish
`score_error` from a real low score. Extracted documents feed scoring, letters
and keywords (fallback to `profile.yaml` JSON if empty/unextractable).
`keywords --apply` writes the German list into the current account's DB row.
`apply` chooses the current profile's CV and writes it as `Lebenslauf.pdf`.

## Accounts

- Multi-profile family web UI: before every page there is `/login` — a "Выбор профиля" dropdown and profile creation. There are intentionally no passwords. Login/creation stores only the stable `account_id` in a signed Flask session; malformed, unsigned, unknown, or stale sessions redirect to `/login`; `/logout` is POST and clears the session.
- Data isolation per account: SQLite `accounts` contains the technical identity (`account_id` UUID + display name + keywords JSON + `gemini_api_key`); one-to-one `candidate_profiles` contains full name, address, email, phone, languages, preferred letter language and search region. Versioned migrations live in `schema_migrations`. `vacancies` uses composite PK `(account_id, refnr)`, an FK to `accounts.account_id`, and account-scoped indexes; `jobs` stores account-scoped background runs, steps, bounded logs and state. `Store(user=...)` resolves the stable ID before every profile/vacancy/job operation. The default account is `"Илья"`; new accounts start empty. A consistent SQLite backup is created before upgrading an existing schema.
- The web UI passes the account to CLI subprocesses via env `CV_AGENT_USER` (merged in `_user_env`); `config.current_user()` = env or `"Илья"`. `config.load_criteria(user=None)` resolves keywords from the account's DB row (authoritative if the account exists, even if empty; fallback to `criteria.yaml` `keywords` only if the account is missing).

## Profile (значок-аватар в правом верхнем углу)

- `/profile` (protected): shows account name; edits account-scoped candidate details (`POST /profile/details`); manages document upload (PDF/TXT/MD only, at most 10 files, 10 MB/file, 50 MB/profile), safe delete, and Gemini API key. The saved key is never rendered back to HTML. Search uses the profile's region when set; scoring/letters include only the current structured profile and documents. Global `profile.yaml` fallback is limited to the legacy default account.
- Per-user documents: before storage migration, `documents.cv_dir(user)` uses legacy `cv/<user>/`; after `migrate-storage --apply`, documents and new dossiers use `data/accounts/<account_id>/{cv,applications,tmp}` through the single containment-checking `account_path` resolver. The migration is dry-run by default, backs up DB/CV/applications, copies documents, reports ambiguous old dossiers without assigning them, and writes the layout marker last. Uploads are validated, written atomically with mode 0600, and may not follow symlinks.
- Gemini keys are per account (Ollama shared): web translation passes the key directly to `LLMClient`; subprocess env never contains it, and CLI loads only the current profile key from SQLite and passes it explicitly. External LLM use in the web UI starts without an extra consent step; viewing a vacancy does not trigger translation automatically.
- Cross-process request limits use flock slot pools under `data/limits/`: source HTTP and health checks share `limits.network_concurrency` slots (4 by default), while each LLM `provider/base_url/model` backend has its own `limits.llm_backend_concurrency` pool (1 by default). A slot covers only the actual request, never retry/429 sleep. Jobs persist network/LLM request counts and queue-wait seconds (schema v10), expose them through status/UI, and external 429 cooldowns remain account/provider-scoped in `llm_rate_limits` with visible `waiting_rate_limit` state.

## Commands

Setup (one time): `python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"`

```
.venv/bin/cv-agent search [--total-limit N] [--per-query-limit N] [--max-keywords N]  # --limit remains an alias for total limit
.venv/bin/cv-agent score [--verbose] [--missing] [--force]  # cached LLM scoring; --force ignores input hashes
.venv/bin/cv-agent write <refnr>        # generate Anschreiben for one vacancy
.venv/bin/cv-agent apply <refnr>        # build dossier (Anschreiben + CV + stelle.txt), marks applied
.venv/bin/cv-agent keywords [--apply]   # LLM extracts DE+EN search keywords from cv/*.pdf (--apply saves them to the current account in the DB)
.venv/bin/cv-agent status               # list stored vacancies
.venv/bin/cv-agent status --archived    # inspect archived vacancies and source status
.venv/bin/cv-agent purge-archived --confirm [--older-than-days N]  # irreversible account-scoped cleanup; applied rows excluded
.venv/bin/cv-agent web                  # web UI at http://127.0.0.1:8000 (port via CV_AGENT_PORT)
.venv/bin/pytest                        # tests (offline, no network/LLM needed)
```

Pipeline order: `search` → `score` → `write`/`apply`. `search` also checks active stored BA vacancies against the API (404 → `unavailable` + archived, never immediate deletion).

## Key facts

- BA API is the working source: `GET /jobboerse/jobsuche-service/pc/v6/jobs` with header `X-API-Key: jobboerse-jobsuche` (public, no OAuth). Response key is `ergebnisliste`, fields: `stellenangebotsTitel`, `firma`, `referenznummer`, `stellenlokationen[0].adresse`. Details: `/pc/v4/jobdetails/{base64url(refnr)}` → `stellenangebotsBeschreibung`. Long multi-keyword `was` queries return 0 hits — search per keyword instead.
- All four sources implement the shared `SearchAdapter` contract (`queries`, `search`, `detail`, `exists`, `refresh`). `run_adapter` isolates each keyword/category, validates normalized vacancies before storage, deduplicates refnrs across sources and prints a per-source found/skipped/error/duration summary. HTTP adapters retry connection/timeout/5xx failures at most three times with bounded exponential backoff; 4xx failures are normalized without retry. Missing upstream IDs use a stable SHA-256 fragment of the normalized job URL, never Python `hash()` or incomplete IDs such as `ss-`/`gi-None`.
- Search semantics: `criteria.yaml` `search` separates `per_query_limit`, the profile-wide `total_limit`, `max_keywords`, `similarity_threshold` and an optional get-in-it category override. `--limit` is a backward-compatible alias for `--total-limit`. The active account's flat keyword list is normalized/case-insensitively deduplicated and treated as German; the English list emitted by `keywords` is informational and is not queried separately. CLI output shows the maximum search-query count plus the maximum stored-BA existence checks. Semantic dedup normalizes title/company/location, honors the configured threshold and compares new results with the current account's stored vacancies.
- Vacancy lifecycle (schema v8): search uses account-scoped upsert and refreshes title/company/location/URL/published/source metadata/`last_seen_at` while preserving score, application status, `applied_at`, translation and a cached description when the new result has none. Active results reactivate archived rows. Stored lifecycle fields are `published_at`, `last_seen_at`, `description_fetched_at`, `description_hash`, `source_status`, `archived_at` and JSON `source_metadata`. BA 404 marks `unavailable`; source errors remain retryable; legacy Indeed rows are `unsupported` and archived. Normal lists/scoring exclude archived rows. Physical deletion is available only through `purge-archived --confirm`, defaults to rows older than 30 days and never deletes `applied` rows.
- StepStone: search page HTML embeds `window.__PRELOADED_STATE__["app-unifiedResultlist"]` with `searchResults.items` (title, companyName, location, url, harmonisedId) — parsed with `json.JSONDecoder().raw_decode` in `StepStoneSearch._parse_embedded` (refnr `ss-<harmonisedId>`); link-regex fallback in `_parse_links`. LinkedIn: guest search page HTML contains `div.base-search-card` cards (title/company/location/link, `data-entity-urn` → refnr `li-<id>`), parsed in `LinkedInSearch._parse`. get-in-it: public API `GET /api/v2/open/job/search` with header `X-Requested-With: XMLHttpRequest` — no full-text search and its city filter is broken, so `GetInItSearch` derives only relevant Berufsfeld categories from account keywords (or `search.getinit_categories`) and applies a local normalized requested-city/remote filter; the configured radius cannot be reconstructed for this source without geodata. Category ids live in `GETINIT_CATEGORIES`; refnr is `gi-<id>`.
- Descriptions are fetched for all active supported sources: `fetch_description(v)` in `search.py` dispatches by source — BA API (`detail(refnr)`), StepStone (job page `application/ld+json` JobPosting → description; needs Referer, warm-up via search page on 403/404), LinkedIn (job view page `div.description__text`; 999 → empty), get-in-it (job page `__NEXT_DATA__` → `jobJob.job.content`). `ensure_description` is shared by `score`/`write`/`apply` and the web vacancy page; every successful fetch, including an empty response, is persisted with SHA-256 and timestamp. Fresh cache is reused for `search.description_ttl_hours` (168 hours by default); unavailable/unsupported rows are not fetched.
- Scoring (schema v9): `score` fetches/persists the description before exclusions, then requires a meaningful title and description. Non-scoreable rows keep an explicit skip reason such as `description_unavailable`. Exclusions are account-independent config scopes for `title`/`company`/`description`, each with whole-word and regex rules; legacy `exclude_keywords` remains readable. Successful rows persist score/reasons/missing plus provider/model, prompt version, candidate/vacancy/description hashes. Unchanged inputs are reused; `score --force` explicitly recalculates. `min_score` is the single current result threshold (`results_min_score` is read only as a legacy fallback), and results use `score >= min_score`.
- LLM: OpenAI-compatible client; provider/model/base_url configured in `criteria.yaml`. Ollama address is set with `OLLAMA_HOST`. The web model cookie contains only a server-side allowlisted option ID, never a client-provided endpoint. Non-Ollama endpoints require HTTPS; known Gemini host and literal loopback/link-local restrictions are validated before client creation. Gemini uses the current profile key from SQLite. If Ollama is down, web jobs show and persist the actual external provider and fall back to it automatically. Versioned prompts use untrusted-data delimiters; keywords/scoring use structured output when supported, strict validation and one repair attempt. Errors and streamed CLI output redact common key/contact patterns. `LLMClient.complete` keeps independent ordinary/429 retries and honors bounded `Retry-After`/provider metadata.
- Config: `criteria.yaml` (region, keywords fallback, cross-process `limits`, `search` limits/categories/dedup threshold/description TTL, scoped exclusions, `min_score`, llm) and `profile.yaml` (structured CV) — both German content. Per-account keywords live in the DB `accounts.keywords` (JSON), see Accounts.
- State: latest SQLite schema v15 (automatic migration on Store open) at `data/applications.db` (`accounts` with per-account `search_params` JSON for the search form, `candidate_profiles`, `vacancies`, `jobs`, `documents`, `artifacts`, `llm_rate_limits`); production storage migration is active, so documents and new letters/dossiers use account UUID directories. Legacy source directories and migration backups remain available for recovery.
- Web UI main page: "Поиск вакансий" button + checkbox "Сгенерировать новые ключевые слова" (default off) → POST `/pipeline` (keywords `--apply` if checkbox on OR account keywords empty → search → score). Submitted form fields (limit/country/region/city) persist per account in `accounts.search_params` (JSON, schema v11) and prefill the form across sessions and restarts. If keywords are needed but `cv/` is empty — warning "Папка cv пуста" and abort. Pipeline state, steps and bounded output live in SQLite with an `account_id`; each profile may have one active run, different profiles may run concurrently, and status/view routes never return another profile's run. Each created job is executed by a separate `python -m cv_agent.job_worker` process addressed by stable `account_id`; a small web-side reaper marks unexpected worker exits `failed`, and `main()` marks leftover active jobs `interrupted` on web restart. Only allowlisted request overrides enter the worker environment, and Gemini keys are never copied there. POST redirects to `/pipeline/<run_id>` where JS polls `/pipeline/<run_id>/status` every 1.5 s. Streaming subprocess output is persisted by `_pipeline_worker`; wall-clock timeout performs terminate/kill/reap and saves `timed_out`. Both DB jobs and legacy `/run` use server-side command/argument allowlists. `wait_pipeline(run_id, user=...)` blocks until done in tests. Scoring/letter prompts contain no hardcoded candidate name; the letter gets the full name from current documents and uses the current display profile only as fallback. Vacancy page: "Создать Anschreiben" button at the bottom → POST `/vacancy/<refnr>/apply` (runs CLI `apply`). `prepare_dossier` updates only the dossier CV date; the source CV stays untouched. `LLMClient.complete` raises `LLMError` after failed attempts — CLI commands report `LLM error`. CLI technical log output (search plan, per-source summaries, scoring/purge messages) is in English.

## Conventions

- Vacancy feedback (schema v15): cards have Подходит (2), Сомнительно (1), Не подходит (0), optional reason <=2000 chars, edit/comment-save/clear. `vacancy_reviews` is account/vacancy scoped with cascading FK cleanup; automatic score/application state are preserved. Saves capture local algorithmic document inputs plus vacancy text, candidate/vacancy hashes and UTC timestamp; no LLM/embedding/source calls. Changed files/types/languages/preferences/vacancy text warn about stale feedback; signed session/account/vacancy/input context rejects stale/cross-account POSTs. `cv_agent.scoring_review --from-feedback --output-dir NEW_DIR` exports already labeled snapshots via read-only SQLite into private 0700/0600 files. These are informal nonblinded feedback, not an independent quality validation.
- Experimental algorithmic scoring: `score --engine algorithmic [--preview --report NEW_PATH]` uses exact rules plus local Ollama embeddings, never a generative client or cloud fallback. Default `scoring.engine` remains `llm` until calibration. SQLite v13 adds account-scoped `embedding_vectors`, explicit engine/algorithm/settings/result metadata and embedding job metrics; v14 adds `candidate_profiles.scoring_preferences` (work_mode, up to 20 cities), edited in the profile UI. `algorithmic.v3` checks explicitly saved preferences with conservative work-mode rules and exact normalized city matches, never infers distance/radius or remote eligibility. Missing preferences keep location unknown (default maximum 90); matching/unrestricted explicit preferences may add up to 10 points. Preference edits invalidate scores but reuse text vectors. Backend cache identity includes the actual model digest, dimensions, prefixes and preparation version; vector requests use a shared embedding flock slot. Preview updates caches/description metadata but preserves scores. Incomplete/semantic results are preliminary. The results table labels and filters engines; vacancy cards show component points, caps, location evidence and bounded account-scoped artifact history. See `docs/ALGORITHMIC_SCORING.md` and `ROADMAP_ALGORITHMIC_SCORING.md`. Tests use fixed vectors; real model smoke is explicitly invoked through `cv_agent.embedding_smoke` or `scripts/check-local-embeddings.sh`. `cv_agent.scoring_evaluation` compares dictionary/Qwen3/BGE-M3 on explicit datasets, replays the production formula and calibrates thresholds on calibration only; it never changes production settings. Synthetic comparison artifacts live under `docs/benchmarks/`. `cv_agent.scoring_review --count 100 --output-dir NEW_DIR` prepares a private, blinded packet from only the current account using read-only SQLite and cached descriptions; files are 0600 under a new 0700 directory, no scores/DB/CV are modified and no models/network are called. Pending human labels are rejected by the benchmark. The 2026-10-06 real packet contains 100 vacancies (80 calibration/20 holdout) under ignored `data/benchmarks/review-2026-10-06/`; it is private, not anonymized or reviewed.
